# Changelog

All notable changes to flame-mcp are recorded here.

## 0.3.0

110 operations in 13 categories (0.2.0 had 98). Twelve operations are new: `project.save`, `segment.read_effect_setup`, `node.read_setup`, `timeline.usage`, `timeline.colour_spaces`, `render.export`, `render.still`, `desktop.sync_record_tc`, `desktop.set_record_tc`, `desktop.get_record_tc`, `desktop.reorder` and `batch.delete`.

### New operations

- New operation `project.save`: saves the project like Flame's Ctrl+S (`PyWorkspace.commit()`). The server does not read the save back, so the call is `ok` when it returns without an exception and `result.readBackDecisive` is false. It runs main-async: a save that outlives the wait returns `pending.handle` for `journal.poll`. It cannot be undone (`undo: unsupported`) and cannot be a step of `plan.run`. It is not Save Desktop (`PyDesktop.save`).
- New operations `segment.read_effect_setup` and `node.read_setup`: read the value of tags in the setup file of a Timeline FX or of a Batch node without changing the project. A tag is read when it occurs exactly once as `<TAG>value</TAG>` (the rule the edit operations read back with); the value is returned as the text of the file, and any other tag is `null` with the reason in `result.problems`. `tags` is 1 to 20 distinct names, checked before anything is sent to Flame. A setup of several files is counted over all of them, and `result.fileOf` names the file by its extension. The setup is saved to a work folder under `<journal dir>/setups` and the folder is removed when the call ends on the Flame side (success, refusal or an exception there); it can stay if Flame dies or the call ends in `TIMEOUT` or `BRIDGE_LOST`, and one older than 7 days is removed the next time a work folder is made. There is no checkpoint and no journal record.
- New operation `timeline.usage`: reports how the sequences use their sources, one `report` per call, read only (it runs on the main thread for up to 5 s, and the Flame UI is stopped meanwhile). `unlinked` lists the video segments whose `source_unlinked` is true or whose type starts with `Unlinked`; `shared` lists a source used by 2 or more segments; `unreferenced` lists the clips none of whose identities (the `file_path` and the source name) is in any scanned segment. A source is told by its identities: a segment's `file_path` and its source name, whichever is not empty; `shared` groups by the first of them (`matchedBy` says which: `filePath` or `sourceName`, the weaker one). A segment with neither is counted in `segmentsWithoutKey` and used by no report. An attribute that cannot be read makes its sequence unreadable (`sequenceErrors` names it). Every `unlinked` and `shared` item has a `selector` that `segment.*` takes as it is (swap sources with `segment.replace` in `plan.run`, one `plan.run` per sequence). `sequences`, `scope`, `max_sequences` (default 50, at most 500) and `sequence_offset` choose and page the sequences (`nextSequenceOffset`, `stoppedEarly` on the time budget). A Batch Clip node's reference is not counted (`batchUsageNotCounted`), so `unreferenced` means "no video segment of a scanned sequence refers to it", not "unused" (a reference from an audio track only, or from anything that is not a segment, is not counted either): do not delete on it alone, and delete with `desktop.delete` one clip at a time after a person has checked it. `unreferenced` judges only for `scope` `all` with no `sequences`, no closed library, every sequence read in one call within the time budget and every attribute readable; otherwise `judged` is false with a `reason` (`scope`, `sequences`, `closedLibraries`, `budget` or `unreadable`) and `items` is empty, and `sequence_offset` is `INVALID_ARGS`. `judgedAgainst` says what the judgement counted.
- New operation `render.export`: writes one clip or sequence to files with an export preset (`PyExporter.export`, in the Foreground, so Flame is occupied while it runs and MCP calls may not be answered; make `timeout_s` long enough). `preset` is the absolute path of an export preset `.xml` and `output_dir` an existing, writable absolute directory; the preset decides the names of the files and whether they go into sub-folders (`result.files` lists them as paths relative to `output_dir`, with `writtenCount`). It writes only into an empty directory, because the preset decides the names and folders of the files and the op cannot tell what it would overwrite: when `output_dir` holds anything that is not hidden the call is `PRECONDITION_UNMET` with `result.existing` (the count and the first 10, listed down to level 3, the entries directly inside `output_dir` being level 1), nothing is journaled and nothing is exported. Hidden entries (names starting with a dot, and what is inside a hidden folder) do not count; a directory that cannot be listed is not taken for an empty one; and right before the export Flame lists the directory again and exports nothing (`CONFLICT`) if something has appeared since. Use a new directory for each export. `/tmp` and `/var/tmp` are refused unless `allow_default_path=true`. `between_marks=true` writes the frames from the in mark up to, but not including, the out mark. What was written is counted afterwards by listing `output_dir` down to level 16 (a file may lie in at most 15 nested folders; a hidden folder is not entered and hidden entries do not count toward the limit of 200000 entries): the new files that are not hidden are the result. None written (also when only folders were made; `result.newFolders`) is `SILENT_NOOP`, an exception of Flame is `FLAME_API_ERROR`, and for an image-sequence preset that does not write one poster frame (with `between_marks` false), fewer files than the target has frames is `FLAME_API_ERROR` with a message starting `partial:` (the files stay). When the listing was cut short (the limit was reached, or a folder that is not hidden cannot be read; `result.countComplete` is false), a count of 0 or one short of the expected files is not judged: the call is `ok` with a note in `degraded` (a return value of `False` stays `FLAME_API_ERROR`). It cannot be undone (`undo: unsupported`) and cannot be a step of `plan.run`. After a `TIMEOUT`, `BRIDGE_LOST` or `BRIDGE_UNAVAILABLE`, `journal.check` asks the bridge for the result (`basis` `handle`), else lists `output_dir` again (`basis` `disk`, an estimate: landed, partial or not_landed; `unknown` when the listing was cut short, in which case a person has to look at `output_dir`, because there is no operation that records a person's answer). `render.export` is also on the list of operations to confirm with the user first (the server's instructions).
- New operation `render.still`: one frame of a clip as a small PNG for checking it. `source` is exactly one of `{target, frame}` and `{path}`. For `{target, frame}`, `target` is a wiretap / path / selection selector of a `PyClip` (a `PySequence` is `SELECTOR_TYPE`) and `frame` counts from 1 up to the duration (anything else is `INVALID_ARGS` before a copy is made); this version supports only clips whose `start_frame` is 1 (another is `PRECONDITION_UNMET`). Flame makes a temporary reference copy of the clip in the reel `flame_mcp_still` of the first reel group of the Desktop (the reel is made when it is not there), gives it the in and out mark of that frame, writes it with the preset `Tiff (16-bit LZW)` in the Foreground (so Flame is occupied while it runs; `timeout_s`), and deletes the copy again, and the reel when the call made it and it holds no clip, sequence or other entry. `result.copy` gives the copy's uid, name and wiretap id. The clip itself is not changed. The copy is deleted only while it still has the uid and name it was given; `result.tempRemoved` says whether it is gone, and a note in `degraded` says where it is when it is not. The preset file is looked for under `<presets root>/<Flame version>/export/presets/...` (`FLAME_MCP_PRESETS_DIR` sets the root); a missing one is `PRECONDITION_UNMET`. `output_dir` is an existing, empty, absolute directory for the original TIFF (the same rules as `render.export`, `/tmp` and `/var/tmp` refused); without it a new directory below the stills directory (`FLAME_MCP_STILLS_DIR`, by default `~/Library/Application Support/flame-mcp/stills`) is used. Exactly one new file must appear: none is `SILENT_NOOP`, two or more is `FLAME_API_ERROR`. `{path}` takes an absolute path of an existing, readable `tif`, `tiff`, `exr`, `dpx`, `png`, `jpg` or `jpeg` file and sends nothing to Flame. The PNG is made by ffmpeg (found through `FLAME_MCP_FFMPEG`, then the PATH, then the `imageio_ffmpeg` package; without one the call is `PRECONDITION_UNMET` before anything is done, and `flame_version_info` reports `ffmpeg`), scaled to at most `max_width` (default 1280, at most 4096; never enlarged) as 8 bit RGB. It is a derived check image, not a deliverable. ffmpeg is judged by its exit code and its output file, not by what it prints. One ffmpeg run may take 15 s and the whole PNG stage (the narrower re-runs included) 30 s, and the server holds its write lock meanwhile; a stage past its limit is a failure like any other. The PNG is named `proxy.png`, one per run directory, and ffmpeg reads the input as one file whatever its name holds. A failure after Flame wrote the frame leaves the call `ok` with `result.proxy` null and a note in `degraded` that names the original (a new call with a `{path}` source makes the PNG alone); with a `{path}` source it is `PRECONDITION_UNMET`. With `inline=true` the PNG is also returned as an image block after the text answer when it is at most `max_image_bytes` (default 1500000); a larger one is made again 0.75 times as wide, up to 4 times, and when it still does not fit it is not attached and a note in `degraded` says so. The text answer and `structuredContent` never hold image data (`result.attachments` names the file). It cannot be undone (`undo: unsupported`) and cannot be a step of `plan.run`. After a `TIMEOUT`, `BRIDGE_LOST` or `BRIDGE_UNAVAILABLE`, `journal.check` decides it like `render.export` and also asks Flame for a leftover copy of the call: it deletes only a copy whose name, duration and marks are the call's record, and reports any other as `CONFLICT` without deleting it.
- New operations `desktop.sync_record_tc`, `desktop.set_record_tc` and `desktop.get_record_tc`: set the Record TC of clips to their Source TC (what flame-tc-sync does). `desktop.sync_record_tc` takes 1 to 50 clip selectors, reads and judges every clip first, and writes `PyClip.start_time` (and `current_time`) to the segment's `source_in` for the clips whose `record_in` differs, one journaled write per clip in one group (`journal.revert` writes the earlier frames back while the clip reads as the call left it). Every clip gets a row with `before` / `after`; a clip it cannot judge is `skipped` with a `reason` and never written (not a clip, library, several versions or segments, a Gap before the media, a frame-rate difference, a DPX source and a source with no Source TC unless `include_risky=true`). `dry_run=true` writes nothing. `desktop.set_record_tc` writes frame numbers to one clip and `desktop.get_record_tc` is the read it is journaled with.
- New operation `desktop.reorder`: puts the clips and sequences of one Desktop reel into another order, in the same reel. `order` lists every entry of the reel once, in the wanted order, each as a uid or a wiretap selector. Flame can only send an entry to the end of its reel, which gives it a new uid, so the call moves the fewest entries that can reach the order with one `desktop.move` (at most 50); the entries that move get new uids, listed in `result.uidMap` as `{name, from, to, selector}`, and the others keep theirs. An order that leaves an entry out, names one twice or names one that is not in the reel is `INVALID_ARGS` before anything is written, and so is an order that needs more than 50 entries moved. An order the reel already has writes nothing (`ok`, `moved` 0, no journal). The reel is read again afterwards; another order is `FLAME_API_ERROR` with `result.after` and `result.expected`. One journal group holds the `desktop_move`; `journal.revert` moves the entries back into the old order with new uids again (`CONFLICT`, nothing moved, when the reel no longer holds the entries the reorder left). Not allowed in `plan.run`.
- New operation `batch.delete`: deletes a Batch group of the Desktop after saving its setup into the work folder (`result.setupPath`); nothing is deleted when the setup cannot be saved. The current group and an open one are refused unless `allow_current=true`, and so is the only Batch group left. It cannot be undone (`undo: none`; create a Batch group and `batch.load_setup` the saved file) and is on the list of operations to confirm with the user first.
- New operation `timeline.colour_spaces`: lists the colour spaces of the segments of a sequence (every version, every video track) and says whether they are mixed (two or more different values read). A value that cannot be read is counted as `unreadable`, never as a colour space, and makes `complete` false. `render.export` of a sequence runs the same check first and refuses a mixed one with `PRECONDITION_UNMET` (Flame asks for a confirmation on such an export that stops its main thread); segments that could not be read are named in `degraded`.

### Smaller responses

- New setting `FLAME_MCP_RESPONSE`: `full` (the default) sends every field as before; `compact` leaves out empty fields, `execution` on success, null members and a `wiretapId` that repeats its selector, and sends a list of 3 or more alike objects as `{columns, rows}`. What sits under `revert`, `inverse`, and `args` keeps its form. Any other value stops the server at start-up. In compact mode the instructions say so in one sentence, and `flame_context` returns the details as `responseFormat`.
- When a compact response is over the size limit, the limit is applied to the full response first, so lists are still replaced with a count instead of the whole response going to a spill file.
- New argument `fields` on `desktop.list_children`, `desktop.list_all`, `desktop.find`, and `timeline.list_segments`: the members of each item to return, in either mode. An unknown name is `INVALID_ARGS`, also when it is in a step of `plan.run`. An item that could not be read keeps its `error`.

### Changes to existing operations

- `*.set_attributes` (the generic attribute ops, e.g. `desktop.set_attributes`) now writes `current_time`, the one PyTime attribute it accepts, instead of refusing every PyTime. The value is `{"frame": int}` or `{"timecode": str}` (or both, which must agree; the `{timecode, frame}` pair a read returns is accepted as it is), with an optional `fps` that must equal the object's own `frame_rate`. Pass a timecode as `hh:mm:ss+ff`, the form a read returns (another spelling can be taken for a different value by `journal.check`). A time outside `start_time` to `start_time + duration - 1` is `INVALID_ARGS` before anything is written. Other PyTime attributes (`start_time` ...) are still refused. `journal.revert` puts the previous time back.
- New argument `groups` on `journal.purge_checkpoints`: 1 to 50 journal group ids (as `journal.list` and `journal.list_checkpoints` show them). The candidates are then the recorded Timeline checkpoints of those groups that are not purged yet, whatever their age. `groups` with `older_than_days` is `INVALID_ARGS`, and so is a group the journal holds no Timeline checkpoint for (a typo, or a group that only has a Batch checkpoint); both are checked before anything is sent to Flame. A group whose checkpoints are all purged already adds no candidate and is listed in `result.groupsAlreadyPurged`. The `token` covers `groups` (not their order). `older_than_days` no longer has a default in the catalog (`default` is null); without `groups` the server still uses 30 days.
- `desktop.delete` now also deletes an empty schematic reel of a Batch group on the Desktop (current or not), where it used to refuse every reel of a Batch group. Still refused: a shelf reel, a reel that holds a clip or a sequence, a reel whose type cannot be read, a Batch group, and the last schematic reel of a group (also when one call lists all of the group's schematic reels). The group's node count is read before and after each delete (`result.deleted[].nodeCountBefore` / `nodeCountAfter`) and a change is `FLAME_API_ERROR`. `journal.revert` makes a new empty schematic reel of the same name with `PyBatch.create_reel`, at the end (uid, place and colour are not restored; `CONFLICT` if the group already has a schematic reel of that name or is gone). Still not a `plan.run` step.

- `desktop.move` no longer refuses a source that is in the destination already. A move into the reel a clip is in puts it at the end with a new uid (use the selector in the result afterwards), and several go in the order given, so a move reorders a reel. `journal.revert` moves it to the end of the same reel again, so it does not restore the old order.
- New argument `position` on `desktop.arrange`: the items are put before the Nth entry the destination already holds (0 = first; omitted or the number of entries = the end). After the items, the entries that were behind that point are sent to the end in their order by one more `desktop.move` into the same reel, in the same journal group (its index is the number of items; an item that fails leaves it not run, and just before it is written the entries are read again: one that has left the destination stops the call with `CONFLICT`). Those entries get new uids; use the selectors in `result.applied[].shifted[].made`. `journal.revert` puts that move back first and then the items, so the reel lists its old order again when that move went through whole and the reel was not changed before the revert. If that move moves only some of the entries, the call ends in `FLAME_API_ERROR` (`partial:`), `result.failed.notMoved` names the ones left, and the order is not restored by the revert. A `position` past the end of the reel, or with more than 50 entries behind it, is `INVALID_ARGS` before anything is written, and so is a move item whose source is an entry of the destination when `position` is below the number of entries (without `position`, or at the end, that move is allowed and goes to the end). `desktop.arrange` no longer refuses a move whose source is in the destination when `position` is left out.

### Fixes

- `journal.check` of a `render.batch` that the bridge answered for now reads `not_landed`, not `failed`, when the render reported no error and wrote nothing. The other render checks already read it that way.
- `node.save_setup` of a Render node no longer fails with `FLAME_API_ERROR`. On Flame 2025.2.4 it writes `.output_node`, `.lut_node`, `.resize` and `.resize_node`, and the op looked for `.render_node`; `result.path` is now the `.output_node` file and `result.files` lists all four.
- `segment.replace` no longer reports `SILENT_NOOP` for a swap that took effect while the source name, the source range, head and tail stayed the same. The verdict now also reads the segment's name and source size. One of the compared values moving gives `result.verified` true, and the moved names are in `result.changed`. When nothing moved and the new clip's name, width or height differs from the segment's, the call is still `SILENT_NOOP`. When nothing moved and the new clip has the segment's name and size, a read cannot tell whether it was swapped: the call is `ok` with `result.verified` false and a notice, so export the segment and compare the pixels.

## 0.2.0

98 operations in 13 categories (0.1.0 had 93). Five operations are new: `desktop.list_all`, `desktop.arrange`, `render.clip`, `segment.edit_effect_setup` and `node.edit_setup`.

### New operations

- New operation `render.clip`: renders the Timeline FX of a clip or sequence in the Foreground and judges it by reading `is_rendered()` back. It cannot be undone, and it is refused for a clip in a library, a clip without Timeline FX, and (unless `force=true`) a clip that is already rendered.
- New operation `desktop.arrange`: builds a Desktop reel in the order given.
  - `items` is a list of `{action: 'move' | 'copy', source}` (1 to 100), each applied as a `desktop.copy` or `desktop.move` of one source. A source named twice (for example a divider clip between others) gives two clips, and the order is kept.
  - Everything that can be refused is checked first with nothing written: a move whose source is already in the destination or in a library, a destination that is not a Desktop reel, and a source used again after its move.
  - The first item that fails stops the call, and the ones before it stay applied (`result.applied`, `result.stoppedAt`). After the last item the reel is read again, and a different order ends in `FLAME_API_ERROR` with `result.order`.
  - One journal group holds one intent per item, and `journal.revert` puts them back newest first. A moved thing goes back to the end of its old reel, so that reel gets its old order back only if the moved things were its last ones.
  - It is not allowed in `plan.run`.
- New operations `segment.edit_effect_setup` and `node.edit_setup`: replace the value of tags in a Timeline FX's or a Batch node's setup file (`values: {tag: value}`) and load the file back, judged by saving the setup again and reading each tag. Only a tag that occurs exactly once as `<TAG>value</TAG>` is replaced; a name or value that could change the structure of the file is `INVALID_ARGS`, and a request that changes nothing is `PRECONDITION_UNMET`. Both can be reverted with `journal.revert` and can be steps of `plan.run`. Measured on a Timewarp: Flame accepted 99 for `TW_FrameMode`, so a matching read-back shows that Flame took the value, not that it means anything.
- New operation `desktop.list_all`: lists what the Desktop and every library hold in one fixed order, one page at a time (`types`, `scope` of `all`, `desktop` or `libraries`, `limit`, `offset`).
  - The order is each Desktop reel group with its reels and their clips and sequences, then the Desktop's Batch groups, then each library with its folders, reels, clips and sequences. An item has the shape of `desktop.find` plus `path`, `location` and `library`.
  - A Batch group is listed by name and uid only and counted in `batchGroupsSkipped` (every Batch group the walk met, also those `types` dropped).
  - A library that is closed, or whose open state cannot be read, is listed, never opened, and named in `closedLibraries` (give `desktop.list_children` a selector of it to look inside).
  - The walk stops reading after a 5 s budget (the first container is always read) and says so in `stoppedEarly`. When a later call's `offset` is at or past what its walk reached because it stopped earlier than the call that gave the offset, the result has `offsetBeyondReached: true` and a `hint`.
  - An entry that cannot be read is an item with `error`, and the walk goes on.

### Changes to existing operations

- Write operations judge what they did by reading it back, by one rule.
  - Nothing changed is `SILENT_NOOP`.
  - Part of the effect (some of the targets, an extra node, a clip at another frame or under another name, some of the frames of a render, a thing made or changed but not all as asked) is `FLAME_API_ERROR` whose message starts with `partial:`. What took effect stays journaled with state `partial` and counts as a later group for `journal.revert`, and `journal.revert` puts it back where the op has one.
  - The right effect with a return value other than `True` is `ok` with a note in `degraded`.
  - A read-back that raised after the write is `FLAME_API_ERROR` and says the write may have been made. What is already known is kept and journaled.
  - This covers `node.create`, `node.delete`, `node.connect`, `node.disconnect`, `node.duplicate`, `action.create_node`, `batch.add_clips`, `batch.iterate`, `render.batch`, `render.clip`, `timeline.overwrite`, `timeline.insert`, `timeline.cut`, `desktop.move`, `desktop.delete`, `desktop.copy`, `desktop.reformat`, `desktop.create` (a Batch group), `timeline.create_sequence` and `journal.purge_checkpoints`.
  - Before, `desktop.move` / `desktop.delete` / `desktop.reformat` returned `ok` with `partial`, read-back differences of `desktop.create`, `timeline.create_sequence` and `desktop.reformat` were warnings only, and some effects with an unexpected return value were `SILENT_NOOP`.
  - `timeline.overwrite` / `insert` also check that the clip starts at the frame asked for, with the clip's name and the length of its used range.
  - A `journal.revert` of a `desktop.move` that puts back only some is `partial:` too.
- `node.create` is `partial:` (`FLAME_API_ERROR`, the nodes stay and `journal.revert` removes them) whenever more than one new node appeared, also when one of them is the node the call returned. The `Group Input` node that Flame makes with a Colour Blend or a Matte Blend is not counted as an extra node and is listed in `result.companions`.
- `segment.replace` on a segment that has a Timewarp adds a note to `result.notices`: a replace shifts the Timewarp's timing by the length of the head (measured on Flame 2025.2.4: `TW_AnchorOffset` of a default Timewarp, the keys of `SpeedTiming` / `DurationTiming` of one with keys; nothing with head 0), and the note says to save the setup before (`segment.effect_save_setup`) and load it after (`segment.effect_load_setup`), each as a call of its own. Saving or loading the setup of a Timeline FX in the same Flame call as `smart_replace_media` of its segment made every clip put on a sequence made later get an extra `Image` effect (seen on Flame 2025.2.4 and 2026.2.3), and Flame 2025.2.4 later hung or crashed in `save_setup`. Separate calls (the steps of `plan.run` are separate calls) did not. This is listed in `flame_context` pitfalls.
- Three read operations give more per item. `timeline.list_segments` takes `include_connections` (default false, video only): each item gets `connections`, the number of other segments `connected_segments()` lists (null when it cannot be read); the page stops after a 5 s budget (the rest are null, `connectionsStoppedEarly` says where). `desktop.list_children` gives each PyClip / PySequence item `width`, `height` and `bitDepth` (null when unreadable). `batch.list` takes `outputs` (default false): each item gets `outputs`, a summary of its Render and Write File nodes (`name`, `kind`, `bypass`, and `destination` or `mediaPath`); like `node_counts` it loads non-current groups and stops at the same time budget.
- `desktop.delete` now also deletes a reel of a Desktop reel group that holds no clip and no sequence. A reel with anything in it, a reel group, a folder, a library, a Batch group, a reel of a Batch group and anything inside a library are refused as before. A reel whose type cannot be read is refused too. An empty reel has no stash; `journal.revert` makes a new empty reel of the same name and type at the end of the same reel group (a new uid; its old position and other attributes such as its colour do not come back), or ends in `CONFLICT` if the group already has a reel of that name.
- `segment.remove_connection` also takes `targets` (1 to 50 segment selectors, instead of `target`): one call removes the connections of several segments. Every target is checked in one read first and a refusal changes no connection; then each target is a call of its own, in order, and a failure stops the call (nothing is retried) with the earlier targets still removed. `result` lists `removed`, `notRemoved`, `unknown` (the call ran but its read-back failed, or it ended without an answer: the connection may be gone) and `alreadyDisconnected` as indexes in `targets`, and `partial` is `{removed, notRemoved}` counts. Measured with a pair of connected segments, removing the connection of one also removes it from the other, so a target whose connection an earlier target already took away is not an error: it is listed in `alreadyDisconnected`. Like the single form it has no checkpoint and no revert, and it is not allowed in `plan.run`.
- `plan.run` takes `result_detail` (`'auto'` by default, `'full'`, `'summary'`). A plan with more than 10 write steps answers with `'summary'`: each step is only its `ok`, `errorCode` and a small `brief` (a failed step also keeps its `error` and `result`), so a large plan's answer stays short and every step's `ok` stays readable. `result.detail` says which was used.
- `plan.run` now takes Batch node edits: a plan that holds `node.create`, `node.delete`, `node.connect`, `node.disconnect`, `node.duplicate`, `node.load_setup`, `action.create_node`, `action.connect`, `batch.create_reel`, `batch.add_clips` (into a schematic reel) or `batch.organize` is one checkpointed write on one Batch group (`result.batch`), with `node.set_attributes` and `action.set_attributes` steps, and one `journal.revert` restores the group. A step that points at a node by the name an earlier `node.create` gave it is resolved automatically; otherwise give the step `late: true`. `batch.iterate` and `batch.create_shelf_reel` stay out of a plan, because shelf reels and iterations are outside a Batch setup and a restore would leave them.
- `render.batch` now also counts the clips a Render node puts into a Desktop reel group (its destination): `result.newClips` lists them, and `render.plan` shows the expected reel as `destinationReel`. The reel is the one a third element of the destination names (Flame 2026.2.3 reads the destination back as `['Reel Groups', <group>, <reel>]`), else `Batch Renders`.
- A resolution (`PyResolution`) can be read and written with `node.get_attributes` and `node.set_attributes`: `{width, height, bit_depth, frame_ratio, scan_mode}`, any of them. Measured on a Colour Source node, `bit_depth` 8, 16 and 32 take and 10 and 12 become 16; on a Clip node width and height take and `bit_depth` does not change. When a write changes the value but not to the one asked for, the call ends in `FLAME_API_ERROR` (`result.failed` starts with `partial:`) with the value read back in `result.after`, for every attribute: before, a number Flame rounded ended in `SILENT_NOOP`. `journal.revert` now also puts back such a write (and the part of a resolution that took); it was refused before. The journal's outcome records these keys as `changedKeys`.
- A restore of a Batch checkpoint (`journal.revert`, `journal.restore_checkpoint`) now lists the clips in the group's reels that came back with fewer Timeline FX (`result.timelineFxLost`) and the clips it could not compare (`result.timelineFxUnchecked`). A Batch setup does not hold those FX.

### Safety and permissions

- Files and folders under `~/Library/Application Support/flame-mcp` are private. New ones are made 0600 (files, also the bridge's result files and the files of an ordered copy) and 0700 (folders), whatever the umask (Flame runs with umask 0). At start the server and the bridge also tighten what is already there: the `flame-mcp` folder, and `run`, `journal` (with `checkpoints`, `setups` and `ordered`), `spill`, `logs` and `bridge` with what is in them, become 0700 / 0600. Only things the user owns are changed; symlinks are not followed or changed, sibling folders such as `scratch` and the content of files are left alone, and a change that fails is logged and skipped. The walk stops after a time and entry limit (only changed entries count), and the next start goes on. The server reports what it did in `flame_version_info` (`result.permissions`). `install_bridge.sh` and `uninstall_bridge.sh` make the folders they create 0700.
- The files `node.save_setup`, `batch.save_setup` and `segment.effect_save_setup` write at a path you chose are made 0600 right after the save (Flame writes them 0666). Only the files that call wrote under the given name are changed, and only regular files you own; a symlink is not followed. `result.madePrivate` lists the files changed and `result.notMadePrivate` the others with the reason; a file that cannot be changed does not fail the call.
- Safety fixes from a review of the whole codebase:
  - Nothing inside a library is deleted, moved or renamed any more. A reel group placed inside a library no longer counts as the Desktop (a target is in a library when any of its parents is one), parents are followed 64 levels instead of 8, and `desktop.delete` / `desktop.move` / `desktop.arrange` refuse what they cannot place on the Desktop. `desktop.rename`, `desktop.set_attributes` and `segment.set_attributes` refuse a library and anything in one (`PRECONDITION_UNMET`, nothing written); the revert of an earlier write is still allowed.
  - `journal.revert` stops with `CONFLICT` when a later group wrote to the same Batch group, sequence or clip and was not reverted (a value write, `desktop.reformat`, `desktop.move`, `desktop.delete`, another checkpointed write; also one whose result is not known or that `journal.check` found diverged), and lists them in `result.newerGroups`, newest first; `force=true` goes ahead. This applies to checkpointed groups (Batch and Timeline) and to the reverts of an in-place `desktop.reformat`, `timeline.create_sequence`, `segment.match` / `segment.copy_to_media_panel` and `desktop.move`. Before, such later writes were put back without a word, because the fingerprint does not look at attribute values or at the format. A write that only makes something new (`desktop.copy`, `segment.match`, ...) does not count.
  - A value write in a bundled Batch `plan.run` is guarded the same way at revert: an attribute changed after the plan makes the revert a `CONFLICT`.
  - Writes are refused until `journal.check` after any write that ended without an answer, also when the answer was a pending handle of a read (`desktop.reformat`'s check no longer lifts the refusal while the reformat still runs), when another call was already waiting for the write lock, when a checkpoint or stash copy or a `journal.purge_checkpoints` batch ended without an answer (released by `journal.check` without a group, `result.unrecorded`), and for `segment.create_connection` and `segment.sync_connections`, which now journal an intent like `segment.remove_connection` and are judged from the segment's stable address.
  - The connection writes are judged by reading back: a count that did not move is `SILENT_NOOP`, one that moved the wrong way `FLAME_API_ERROR`; a sync compares the connected segments before and after.
  - The Timeline restore that `journal.revert` runs (and the in-place `desktop.reformat` revert) needs `destructive` in `FLAME_MCP_ALLOW_EFFECTS`, like the Batch restore.
  - A bundled `plan.run` that stopped after a write ran reads `partial` (not `failed`) in `journal.list` and is listed as a later group; one that stopped before any write ran has nothing to revert. `plan.run` no longer takes a `values` dict of `node.edit_setup` for a node selector.
  - `journal.restore_checkpoint` and `batch.load_setup` say that they overwrite without comparing with the current state (the state before is kept in `result.preCheckpoint`) and are in the list of operations to confirm with the user.

### Documentation and reporting

- The README says that flame-mcp is in beta: try it on a test project first, use read-only mode to only look, and send a short usage report even when nothing went wrong.
- GitHub issue forms for a bug report, a request and a usage report. Each form needs only one field, and a blank issue can still be opened.
- `docs/safety.md` lists, under What cannot be undone, the state of a Flame session after a replace and a setup save or load in one call.

### Fixes

- Fixed: `desktop.copy` decides what it made from the destination's new entries, not from Flame's answer. An empty answer with a grown destination used to be `SILENT_NOOP` and left no journal record.
- Fixed: a thing `desktop.move` moved but could not pair by its answer or name is paired by position (`moved[].pairedBy`) when its old uid is gone and it is the only such source of its type, so `journal.revert` no longer misses it. With two or more of one type none is paired; they are listed in `notMoved` with `uidGone: true`.
- Fixed: `journal.purge_checkpoints` reports a stashed copy that `flame.delete` left in place (`result.notDeleted`) instead of counting it as skipped.
- `journal.revert` can now put back a group that wrote the same key of the same target more than once (for example a `plan.run` that set one attribute in several steps). Before, it refused with CONFLICT because it compared every one of those writes to the current value; now only the newest is, and each earlier one is compared to the value the next write found.
- `segment.trim` and `segment.slip` no longer fail when a head or tail was `'infinite'` before the edit: that side is not judged, and `result.handleJudged` says which sides were.

## 0.1.0

First public release.

- Lets an MCP client, such as Claude Code, read and edit a running Autodesk Flame. There are 93 operations in 13 categories: reading, organizing, editing, Batch, and multi-step plans (`plan.run`). See [docs/ops.md](docs/ops.md) for the full list.
